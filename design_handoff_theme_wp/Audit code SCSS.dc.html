Préparer un SCSS
qui tient debout

Ta question est la bonne : un SCSS n'est utile que s'il décrit un système déjà cohérent. J'ai donc mesuré le code des 22 pages avant de proposer quoi que ce soit — voici ce qu'il y a vraiment dedans, et l'architecture qui en découle.

37 602 déclarations de style 777 valeurs déjà alignées 13 composants à définir

Mon avis, en bref

Le site est en réalité très systématique : un seul motif de card, un seul bouton, une nav et un pied de page identiques partout. Ce qui manque, ce n'est pas la cohérence du design — c'est qu'elle n'est écrite nulle part : chaque valeur est recopiée à la main dans le balisage, donc elle dérive silencieusement.

Passer au SCSS est donc surtout un travail de nommage : 37 602 déclarations se ramènent à une trentaine de décisions. Et la dérive n'est pas théorique — la mesure en a trouvé une, visible à l'œil nu, expliquée juste en dessous.

Deux palettes cohabitaient dans le code — une seule était réellement affichée

Chaque couleur du site s'écrit avec une valeur de secours : utilise la variable, ou à défaut ce code hexadécimal. Sur l'accueil, ces valeurs de secours étaient restées sur une palette abandonnée en début de projet (#59b529 au lieu de #7bc62f). À l'écran, rien ne se voyait — la variable était bien définie, donc le secours ne servait jamais. Mais en traduisant vers le SCSS, c'est le code écrit qui aurait été lu, pas le rendu.

En SCSS, le problème disparaît de toute façon par construction : une variable, pas de secours possible.

Une seule règle de nommage

.c-card, .c-card__titre, .c-card--vignette. Un préfixe c- pour les composants, l- pour les mises en page : dans un thème WordPress, ça évite les collisions avec le CSS du thème parent.

Deux points de bascule, pas plus

Le site n'a que deux seuils : 640 px (téléphone) et 900 px (déplié). Ils sont déjà partout dans le code, appelés 1 183 fois. Deux mixins suffisent : @include phone et @include foldable.

Le survol : 30 → 6

30 variantes de survol pour six comportements réels. Le plus fréquent (715 fois !) est l'item de menu du burger. Six mixins couvrent tout : lien de nav, item de burger, card cliquable, bouton vert, bouton fantôme, lien de pied de page.

Et le passage en rem

Les huit pas de texte s'écrivent en rem, dérivés d'une taille de base unique. C'est ce qui rend possible le réglage de police du plugin : Source Sans 3 paraît 11 % plus petite qu'Inter, et sa correction se fait alors en changeant une valeur au lieu de 2 758. Sans cette conversion, le choix de police ne peut pas être proposé au client.
